## 1. Concept Summary

### OLTP vs OLAP

| | OLTP (operational) | OLAP (analytical) |
|---|---|---|
| Purpose | Run the business (place an order) | Analyze the business (revenue trends) |
| Schema | Highly normalized (3NF) | Denormalized (star/snowflake) |
| Workload | Many small reads/writes | Few large scans/aggregations |
| Example | Application database | Data warehouse |

### Normalization (OLTP-style modeling)

| Form | Rule |
|------|------|
| 1NF | Atomic values, no repeating groups |
| 2NF | 1NF + every non-key column depends on the **whole** primary key (matters for composite keys) |
| 3NF | 2NF + no non-key column depends on another non-key column (no transitive dependency) |

Normalization avoids update/insert/delete anomalies and duplicate storage, at the cost of more joins.

### Dimensional modeling (OLAP-style modeling)

- **Fact table**: the measurable events (orders, sales). Contains **foreign keys** to dimensions and **numeric measures** (quantity, revenue). One row = one grain (see below).
- **Dimension table**: descriptive context (customer, product, date). Wide, relatively few rows, changes slowly.
- **Star schema**: fact table directly joined to denormalized dimensions (fast, simple, most common in warehouses).
- **Snowflake schema**: dimensions further normalized into sub-dimensions (saves storage, more joins, less common today given cheap storage).
- **Grain**: the definition of what one fact row represents ("one line item per order", not "one order"). Decide the grain **first**, before adding any column. Every measure must be true at that grain.

### Fact table types

| Type | Example | Additivity |
|------|---------|------------|
| Transaction fact | One row per sale | Fully additive (revenue can be summed on any dimension) |
| Periodic snapshot | End-of-day account balance | Semi-additive (cannot sum across time, can sum across accounts) |
| Accumulating snapshot | Order lifecycle (order -> ship -> deliver), one row updated as it progresses | Mixed; tracks milestone dates |

### Slowly Changing Dimensions (SCD)

Handling changes to dimension attributes over time (a customer moves city, changes tier):

| Type | Behavior | Trade-off |
|------|----------|-----------|
| **Type 0** | Never changes (original value kept forever) | Simplicity, loses history by design |
| **Type 1** | Overwrite the old value | No history. Simple, small |
| **Type 2** | Insert a new row with a surrogate key and a validity range (`valid_from`, `valid_to`, `is_current`) | Full history. More rows, fact joins need the date range |
| **Type 3** | Add a new column for the previous value | Only remembers one prior state |
| **Hybrid** | Mix of the above per attribute | Matches real business rules |

A **surrogate key** (a meaningless, sequential key, generated by the warehouse) identifies each **version** of a dimension row, while the **business/natural key** (e.g. `customer_id`) identifies the real-world entity across versions. Facts join to the surrogate key that was current at the time of the event, not to the natural key.

### Joining a fact to an SCD Type 2 dimension

```sql
SELECT f.*, d.segment
FROM fact_sales f
JOIN dim_customer_scd2 d
  ON f.customer_id = d.customer_id
 AND f.sale_date >= d.valid_from
 AND f.sale_date <  d.valid_to;
```
This finds the dimension row that was valid **on the date of the fact**, giving the correct historical attribute instead of always the current one.

### Keys

- **Natural/business key**: meaningful in the source system (`customer_id`, an email).
- **Surrogate key**: a warehouse-generated key (usually an integer), stable and meaningless, used for joins and to support SCD Type 2.
- **Primary key**: uniquely identifies a row in a table.
- **Foreign key**: a column referencing another table's primary key. Fact tables carry foreign keys to dimension surrogate keys.

### Modeling approaches for a warehouse

| Approach | Idea |
|----------|------|
| Kimball (dimensional) | Star schemas per business process, bottom-up, easy for BI tools |
| Inmon (normalized EDW) | Normalized enterprise warehouse first, dimensional marts built from it |
| Data Vault | Hubs (business keys), links (relationships), satellites (attributes and history); built for auditability and change tolerance in raw/ingestion layers |
| Medallion (bronze/silver/gold) | Raw -> cleaned/conformed -> business-ready aggregated layers; common in lakehouses, complements the above |

## 4. Examples with Explanations

### 4.1 Grain check: revenue per customer from the fact table
```sql
SELECT customer_id, SUM(revenue) AS total_revenue
FROM fact_sales
GROUP BY customer_id
ORDER BY customer_id;
```

**Result:**

| customer_id | total_revenue |
|---|---|
| 101 | 2200 |
| 102 | 1360 |

The fact table's grain is one row per sale, so summing `revenue` at any coarser grain (customer, date, product) is always valid. That is what "fully additive" means.

### 4.2 Point-in-time SCD Type 2 join
```sql
SELECT f.sale_id, f.date_key, d.customer_name, d.segment
FROM fact_sales f
JOIN dim_customer_scd2 d
  ON f.customer_id = d.customer_id
 AND (f.date_key || '') >= REPLACE(d.valid_from, '-', '')
 AND (f.date_key || '') <  REPLACE(d.valid_to,   '-', '')
ORDER BY f.sale_id;
```

**Result:**

| sale_id | date_key | customer_name | segment |
|---|---|---|---|
| 1 | 20240105 | Anil | Standard |
| 2 | 20240110 | Bina | Standard |
| 3 | 20240212 | Anil | Premium |
| 4 | 20240301 | Bina | Standard |
| 5 | 20240315 | Bina | Standard |
| 6 | 20240402 | Anil | Premium |

Sale 1 (Jan 2024) joins to Anil's **Standard** version. Sale 3 (Feb 12, 2024) joins to his **Premium** version, because his segment changed on Feb 1. A naive join on `customer_id` alone (ignoring the date range) would show Premium for both, rewriting history.

### 4.3 The wrong way: joining only on the natural key
```sql
SELECT f.sale_id, f.date_key, d.segment
FROM fact_sales f
JOIN dim_customer_scd2 d ON f.customer_id = d.customer_id
WHERE f.customer_id = 101
ORDER BY f.sale_id;
```

**Result:**

| sale_id | date_key | segment |
|---|---|---|
| 1 | 20240105 | Premium |
| 1 | 20240105 | Standard |
| 3 | 20240212 | Premium |
| 3 | 20240212 | Standard |
| 6 | 20240402 | Premium |
| 6 | 20240402 | Standard |

This duplicates every one of Anil's sales, once per dimension version (fan-out, see Topic 2), and cannot tell you which segment applied at the time of each sale. This is why SCD2 joins must include the date range.

### 4.4 Only the current dimension row (typical for a 'current state' report)
```sql
SELECT customer_id, customer_name, segment
FROM dim_customer_scd2
WHERE is_current = 1
ORDER BY customer_id;
```

**Result:**

| customer_id | customer_name | segment |
|---|---|---|
| 101 | Anil | Premium |
| 102 | Bina | Standard |

`is_current` (or `valid_to = '9999-12-31'`) is a convenience flag so you do not need a date comparison when you only want today's picture.

## 5. Interview Questions and Answers

### Basic

**Q1. OLTP vs OLAP: what is the difference?**
OLTP systems run the business with many small, fast reads and writes on a normalized schema (an application database). OLAP systems analyze the business with large scans and aggregations on a denormalized schema (a data warehouse). Data pipelines typically move data from OLTP sources into an OLAP-modeled warehouse.

**Q2. What is normalization? Briefly describe 1NF, 2NF, 3NF.**
Organizing tables to reduce redundancy and avoid update anomalies. 1NF: atomic values, no repeating groups. 2NF: every non-key column depends on the whole primary key. 3NF: no non-key column depends on another non-key column (no transitive dependency).

**Q3. What is a fact table? What is a dimension table?**
A fact table stores measurable business events with foreign keys to dimensions and numeric measures (e.g. one row per sale, with `quantity`, `revenue`). A dimension table stores descriptive context (customer, product, date) used to filter and group facts.

**Q4. Star schema vs snowflake schema?**
Star: fact table joined directly to denormalized dimensions (fewer joins, simpler, common in warehouses). Snowflake: dimensions are further normalized into sub-dimensions (less redundancy, more joins).

**Q5. What is the "grain" of a fact table?**
The precise definition of what one row represents (e.g. "one row per order line item"). It must be decided before adding any measure, and every measure must be true at that grain. Mixing grains in one fact table is a common modeling bug.

### Intermediate

**Q6. What are Slowly Changing Dimensions? List the types.**
Techniques for handling changes to dimension attributes over time. Type 0: never changes. Type 1: overwrite (no history). Type 2: new row with a validity range (full history). Type 3: new column for the previous value (one prior state only). Hybrid: mix per attribute.

**Q7. Walk through how you would implement SCD Type 2.**
On each load, compare incoming rows to the current dimension row by business key. If an attribute you track changed, close the old row (`valid_to = load_date`, `is_current = 0`) and insert a new row (`valid_from = load_date`, `valid_to = '9999-12-31'`, `is_current = 1`, new surrogate key). Unchanged rows are left alone. This is typically done with a `MERGE`/upsert.

**Q8. Why do fact tables reference dimension surrogate keys instead of natural keys?**
So a fact row can point to the exact dimension **version** that was true at the time of the event, supporting SCD Type 2. Natural keys alone cannot distinguish between versions and would cause fan-out when joined to a Type 2 dimension.

**Q9. Difference between transaction, periodic snapshot, and accumulating snapshot fact tables?**
Transaction: one row per event, fully additive. Periodic snapshot: one row per entity per time period (e.g. daily balance), semi-additive (cannot sum across time). Accumulating snapshot: one row per process instance, updated in place as it moves through milestones (e.g. order lifecycle), useful for lag/duration analysis between stages.

**Q10. What is a junk dimension and a degenerate dimension?**
A junk dimension bundles several small, low-cardinality flags/indicators (e.g. `is_gift`, `payment_method`) into one dimension table to avoid many tiny dimensions. A degenerate dimension is an identifier that lives directly in the fact table with no separate dimension table (e.g. an order number), because it has no other attributes.

**Q11. Why might you still denormalize even though it duplicates data?**
Denormalized star schemas trade storage (cheap) for fewer joins and simpler, faster analytical queries and simpler BI tool modeling. Storage is rarely the constraint in a modern warehouse; query simplicity and speed usually matter more.

**Q12. What is a bridge table?**
A table resolving a many-to-many relationship between a fact and a dimension (or between two dimensions), for example a customer having multiple email addresses, or an order fulfilled from multiple warehouses. Prevents fan-out that a direct many-to-many join would cause.

### Advanced

**Q13. How do you handle late-arriving dimension changes or late-arriving facts?**
Late-arriving dimension: insert a placeholder/"early arriving fact" row and backfill attributes when the dimension data arrives, or delay fact processing until the dimension is available (with monitoring for delay). Late-arriving fact: insert it with the dimension version that was valid **at the fact's actual event time** (not today's current version), using the SCD2 date range join.

**Q14. Compare Kimball, Inmon, and Data Vault at a high level.**
Kimball: bottom-up, dimensional star schemas per business process, fast to build, BI-friendly. Inmon: top-down, a normalized enterprise data warehouse first, with dimensional data marts built from it, more consistency but slower to deliver. Data Vault: hubs (business keys), links (relationships) and satellites (attributes with history), designed for auditability, parallel loading and tolerance to source changes, often used as a raw/integration layer feeding Kimball-style marts.

**Q15. How does the medallion architecture (bronze/silver/gold) relate to dimensional modeling?**
Bronze: raw, unmodified source data. Silver: cleaned, conformed, deduplicated, often close to 3NF or a lightly modeled layer. Gold: business-ready, typically dimensional (star schema) or highly aggregated tables that BI tools query directly. Dimensional modeling usually happens in the silver-to-gold transition.

**Q16. How would you model a many-to-many relationship in a fact table without fan-out?**
Use a bridge/associative table with a weighting factor if needed (e.g. splitting a sale's revenue across multiple sales reps), or restate the fact at a finer grain that resolves the many-to-many naturally (e.g. one row per order-product instead of one row per order when products vary in count).

**Q17. What is the difference between a surrogate key and a hash key, and when would you use a hash key?**
A surrogate key is typically an auto-incrementing integer generated by the warehouse. A hash key (e.g. `MD5`/`SHA` of the business key) is deterministic, so it can be computed independently across parallel loads without a lookup/coordination step, which is why Data Vault uses hash keys for hubs and links. Trade-off: hash collisions are extremely unlikely but theoretically possible, and hash keys are larger and less human-readable than sequential integers.

**Q18. How do you decide the grain of a new fact table with a stakeholder?**
Ask what one row should represent in a full sentence ("one row per X"), confirm every requested measure is true at that grain (not double-counted or averaged incorrectly), check it against the most detailed reporting requirement (you can always aggregate up, never disaggregate down), and document it before building anything.

### How to practice (write, run, test, then look at the solution)

1. **Set up the data.** Run [`09-data-modeling-setup.sql`](./09-data-modeling-setup.sql) in any database (Postgres, Snowflake, MySQL, SQLite, or an online tool such as DB Fiddle).
2. **Write your own query** for the problem.
3. **Compare with the Expected Output** under each problem.
4. **Run the self-check query** (template below). **0 rows returned = correct.**
5. Only then open the **Solution**.

### Self-check template

```sql
WITH my_answer AS (
    -- paste YOUR query here (example below is the solution to P1)
    SELECT product, SUM(revenue) AS total_revenue
    FROM fact_sales
    GROUP BY product
),
expected (product, total_revenue) AS (
    VALUES ('Phone', 1800),
           ('Laptop', 1600),
           ('Mouse', 160)
)
SELECT 'MISSING' AS issue, m.* FROM (SELECT * FROM expected  EXCEPT SELECT * FROM my_answer) m
UNION ALL
SELECT 'EXTRA'   AS issue, e.* FROM (SELECT * FROM my_answer EXCEPT SELECT * FROM expected)  e;
```

Notes:
- Column names and order in `my_answer` must match `expected`.
- `EXCEPT` ignores row order, so for problems marked "order matters", also compare the order by eye.
- Dialects: BigQuery needs `EXCEPT DISTINCT`, Oracle uses `MINUS`. SQL Server / older MySQL need `SELECT ... UNION ALL SELECT ...` instead of `VALUES (...)`. SQL Server also does not allow `ORDER BY` inside a CTE, so remove it from `my_answer`.
- No `EXCEPT` available? Just compare with the Expected Output table by eye.

### P1. Total revenue by product from the fact table.

Return `product` and `total_revenue`, highest revenue first.

**Expected output (order matters):**

| product | total_revenue |
|---|---|
| Phone | 1800 |
| Laptop | 1600 |
| Mouse | 160 |

<details><summary>Solution</summary>

```sql

FROM fact_sales
GROUP BY product
ORDER BY total_revenue DESC
```

Because the fact grain is one row per sale, summing revenue at the product level is always valid (fully additive).

|---|---|---|
| 101 | Anil | Premium |

### P4. How many historical (non-current) versions does each customer have in the SCD2 dimension?

Return `customer_id` and `historical_versions` (count where `is_current = 0`). Include customers with 0.

**Expected output (order matters):**

| customer_id | historical_versions |
|---|---|
| 101 | 1 |
| 102 | 0 |

<details><summary>Solution</summary>

```sql
SELECT customer_id, SUM(CASE WHEN is_current = 0 THEN 1 ELSE 0 END) AS historical_versions
FROM dim_customer_scd2
GROUP BY customer_id
ORDER BY customer_id
```
Anil (101) has 1 historical version. Bina (102) has 0, and still shows up because `SUM(CASE ...)` is used instead of filtering rows out with `WHERE`.
</details>

## 7. Common Mistakes

1. Joining a fact table to an SCD Type 2 dimension on the business key only, without the date range (fan-out and wrong historical attributes).
2. Not deciding the fact table's grain before adding measures, leading to double counting.
3. Using natural keys as foreign keys in the fact table instead of surrogate keys.
4. Treating a semi-additive measure (balance, inventory) as fully additive and summing it across time.
5. Over-normalizing a warehouse's reporting layer, forcing every BI query through many joins.
6. Confusing Type 1 (overwrite) with Type 2 (history) and silently losing history the business needed.
7. Forgetting to close the old row (`valid_to`, `is_current = 0`) when inserting a new SCD2 version.
8. Mixing several fact grains in one table (e.g. order-level and line-item-level rows together).
9. Ignoring late-arriving facts/dimensions and always joining to today's current dimension version.
10. Building star schemas before agreeing on the grain and definitions with stakeholders.

## 8. Quick Revision Notes

- OLTP = normalized, transactional. OLAP = denormalized, analytical.
- 1NF atomic values, 2NF full key dependency, 3NF no transitive dependency.
- Star schema: fact (events + measures + FKs) + denormalized dimensions. Snowflake: dimensions further normalized.
- Grain = what one fact row represents. Decide it first, every measure must hold at that grain.
- SCD Type 0 never changes, Type 1 overwrite, Type 2 full history (surrogate key + valid_from/valid_to), Type 3 one prior value.
- Fact tables use surrogate keys to reference the dimension version valid at the event time.
- SCD2 join: business key match AND event date between valid_from and valid_to.
- Transaction fact (additive) vs periodic snapshot (semi-additive) vs accumulating snapshot (milestones).
- Bridge table resolves many-to-many without fan-out. Junk dimension bundles small flags.
- Kimball (dimensional, bottom-up), Inmon (normalized EDW, top-down), Data Vault (hubs/links/satellites), medallion (bronze/silver/gold).
